DOCUMENTACION DEL PROYECTO GO MEDICAL - APP MOVIL
Ultima actualizacion: 28 de julio de 2026

Este documento explica la estructura del codigo de la app movil Go Medical,
las pantallas principales, los servicios que conectan con Supabase, los modelos
de datos, los recursos visuales y la forma recomendada de presentar el proyecto.

No contiene credenciales, llaves privadas ni tokens de administracion.


1. RESUMEN GENERAL

Go Medical es una aplicacion movil desarrollada en Flutter para un marketplace
de equipo medico y servicios biomedicos.

La app permite:

- Iniciar sesion y registrarse con Supabase Auth.
- Consultar productos, categorias, subcategorias, banners y promociones desde
  Supabase.
- Ver detalle de productos, imagenes, caracteristicas, preguntas y opiniones.
- Agregar productos al carrito.
- Solicitar cotizaciones.
- Preparar el flujo de pago con Mercado Pago desde backend.
- Guardar direcciones de entrega.
- Programar solicitudes de mantenimiento biomedico.
- Crear y consultar tickets de soporte.
- Administrar favoritos, historial, opiniones, compras y notificaciones.

Tecnologia principal:

- Flutter / Dart.
- Supabase Auth.
- Supabase Database.
- Supabase Storage.
- Supabase Edge Functions.
- Google Sign-In.
- Mercado Pago preparado mediante Edge Function.
- Flutter Map / OpenStreetMap para ubicaciones.


2. ESTRUCTURA PRINCIPAL DEL CODIGO

El codigo de la app se encuentra principalmente dentro de la carpeta lib.

Estructura general:

lib/
- main.dart
- models/
- screens/
- services/
- utils/
- widgets/

Descripcion:

- lib/main.dart:
  Punto de entrada de la app. Inicializa configuracion, Supabase, servicios
  globales, tema visual y flujo inicial de autenticacion.

- lib/models/:
  Modelos Dart que representan datos recibidos desde Supabase o usados por la
  interfaz.

- lib/screens/:
  Pantallas visibles de la aplicacion. Aqui se encuentran login, home,
  categorias, producto, carrito, perfil, tickets, cotizaciones, pagos,
  direcciones y mantenimiento.

- lib/services/:
  Capa de comunicacion con Supabase y servicios externos. Aqui se centralizan
  consultas, inserciones, actualizaciones y llamadas a Edge Functions.

- lib/utils/:
  Constantes, helpers visuales y configuraciones reutilizables.

- lib/widgets/:
  Componentes visuales compartidos entre pantallas.


3. ARRANQUE DE LA APLICACION

Archivo principal:

lib/main.dart

Responsabilidades:

- Cargar valores de entorno desde dart-define.
- Validar si existen credenciales de Supabase.
- Inicializar Supabase.
- Inicializar servicios globales.
- Configurar tema visual.
- Mostrar Login, Registro o Home segun el estado del usuario.

Flujo inicial:

1. La app lee SUPABASE_URL y SUPABASE_ANON_KEY.
2. Si faltan credenciales, muestra una pantalla de configuracion pendiente.
3. Si las credenciales existen, inicializa Supabase.
4. Revisa si hay sesion activa.
5. Si hay sesion, valida el checklist de registro.
6. Si todo esta correcto, abre HomeScreen.
7. Si no hay sesion, abre LoginScreen.

Pantallas relacionadas:

- MissingConfigScreen:
  Se muestra cuando no se pasan las variables necesarias por dart-define.

- AuthGate:
  Decide si el usuario entra al login, registro pendiente o pantalla principal.


4. CREDENCIALES Y CONFIGURACION

Archivo:

lib/utils/constants.dart

La app lee las credenciales asi:

- SUPABASE_URL
- SUPABASE_ANON_KEY
- GOOGLE_ANDROID_CLIENT_ID
- GOOGLE_WEB_CLIENT_ID

Estas variables se cargan por compilacion usando dart-define.

Ejemplo de ejecucion local:

flutter run --dart-define-from-file=dart_defines.json

Importante:

- dart_defines.json es local y no debe subirse al repositorio.
- dart_defines.example.json debe contener solo ejemplos sin valores reales.
- La anon key de Supabase es publica, pero depende de RLS para ser segura.
- La service_role key nunca debe estar dentro de Flutter.

12. SEGURIDAD ACTUAL

Medidas ya trabajadas:

- Las credenciales se cargan por dart-define.
- dart_defines.json no debe subirse al repositorio.
- ProductService usa columnas publicas explicitas para productos.
- La app no debe usar service_role.
- Mercado Pago debe calcular montos desde backend, no desde Flutter.
- process_cart_checkout no debe estar disponible para anon.

Puntos que deben seguir revisandose en Supabase:

- Politicas RLS reales de todas las tablas.
- Permisos de funciones RPC.
- Buckets privados para archivos sensibles.
- Columnas publicas contra columnas internas.
- Flujo real de pago con webhook antes de descontar inventario.


13. PROMOCIONES Y TIEMPO

Regla recomendada:

Las promociones no deben depender del reloj del telefono.

La app debe leer desde Supabase:

- Fecha de inicio.
- Fecha de fin.
- Estado activo.
- Prioridad.
- Producto o categoria aplicable.

La validacion final debe ocurrir en backend usando tiempo del servidor.

Esto evita que un usuario cambie la fecha del telefono para activar o extender
promociones.

20. RESUMEN PARA PRESENTACION CORTA

Go Medical es una app Flutter conectada a Supabase. La aplicacion separa las
pantallas en screens, la comunicacion con la base en services y los datos en
models. El home consume categorias, banners y productos desde Supabase. El
carrito, direcciones, cotizaciones, opiniones, tickets y solicitudes de
mantenimiento se guardan en la base de datos. El pago con Mercado Pago esta
preparado para que el backend cree la preferencia y valide los montos, sin que
Flutter envie precios ni totales. Las credenciales se cargan por dart-define y
no deben subirse al repositorio.


21. REVISION DE CONTRATO MOVIL Y BACKEND (2026-07-29)

Identidad:

- Los flujos de negocio autenticados obtienen clients.id exclusivamente desde
  profiles.client_id.
- auth.uid() se usa como identidad de autenticacion y no como clients.id.
- Si no existe vinculacion, la app detiene la operacion con un mensaje claro.
- Se elimino la creacion o actualizacion automatica de filas en clients desde
  la app movil.

Carrito y cupones:

- El carrito sigue usando carts y cart_items.
- Flutter no envia unit_price al agregar productos.
- Los cupones usan solamente las RPC existentes:
  apply_cart_coupon(p_cart_id, p_code),
  get_cart_pricing(p_cart_id) y
  remove_cart_coupon(p_cart_id).
- La app interpreta valid, reason y message, pero no calcula descuentos ni
  reemplaza los totales autoritativos del backend.
- La consulta de telefonos queda detras de check_phone_exists; no existe
  respaldo que consulte directamente la tabla clients.

Tickets:

- Los mensajes nuevos usan sender_id igual al UUID autenticado,
  sender_type=client e is_internal=false.
- Las consultas del cliente filtran is_internal=false.
- La propiedad del ticket se valida mediante profiles.client_id.
- Los archivos se guardan en el bucket privado ticket-attachments con la ruta
  ticket_id/uuid.extension.
- En la base se conserva una referencia de Storage, no una URL firmada.
- Para visualizar o descargar se genera una URL firmada temporal.

Preguntas, catalogo y promociones:

- La creacion de preguntas usa submit_product_question.
- Categorias y subcategorias se consumen activas y ordenadas desde Supabase.
- Banners y tarjetas consumen active_promotion_banners y
  active_promotion_cards.
- La app no recalcula vigencias promocionales con el reloj del telefono.
- sales_count se usa solo para presentacion.

Mercado Pago y checkout:

- La funcion create-mp-test-preference permanece como integracion de prueba.
- Flutter no debe enviar precios, descuentos, impuestos ni totales a Mercado
  Pago.
- process_cart_checkout no debe ser ejecutable por anon ni authenticated.
- Antes de produccion falta validar el webhook, la idempotencia, el pago
  aprobado y el descuento de inventario en el backend.

Modulos no implementados:

- No se encontro un modulo movil de documentos privados de producto.
- No se encontro un flujo movil de devoluciones que use return_requests.
- Estos puntos se reportan como pendientes de integracion y no se inventaron
  tablas, columnas ni RPC nuevas desde Flutter.
