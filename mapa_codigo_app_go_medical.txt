MAPA DEL CODIGO DE LA APP GO MEDICAL
Ultima actualizacion: 28 de julio de 2026

Este archivo sirve para explicar el proyecto movil Go Medical a otra persona
del equipo, mostrar como esta organizada la app y ubicar rapidamente donde esta
el codigo de cada pantalla, servicio y flujo importante.

No contiene credenciales, llaves privadas ni datos sensibles.


1. RESUMEN DEL PROYECTO

Go Medical es una app movil Flutter para un marketplace de equipo medico. La
app permite:

- Iniciar sesion o registrarse con Supabase Auth.
- Consultar productos, categorias, subcategorias, banners y promociones desde
  Supabase.
- Ver detalle de productos, imagenes, caracteristicas, preguntas y opiniones.
- Agregar productos al carrito.
- Solicitar cotizaciones.
- Probar el flujo preparado de Mercado Pago mediante una Edge Function.
- Guardar direcciones de entrega.
- Programar servicios de mantenimiento biomédico.
- Crear y consultar tickets de soporte.
- Administrar favoritos, historial, opiniones, compras y notificaciones.

Tecnologia principal:

- Flutter / Dart.
- Supabase Auth, Database, Storage, Realtime y Edge Functions.
- Android como plataforma movil principal en esta etapa.
- flutter_custom_tabs para abrir checkout externo de Mercado Pago.
- flutter_map, geolocator y latlong2 para ubicacion y mapa.
- image_picker, file_picker y video_player para adjuntos, fotos y video.


2. ESTRUCTURA GENERAL DEL CODIGO

Raiz del proyecto:

- pubspec.yaml
  Define nombre del paquete, dependencias, assets e iconos.

- dart_defines.json
  Archivo local con credenciales de desarrollo. Esta ignorado por Git y no debe
  subirse al repositorio.

- dart_defines.example.json
  Ejemplo sin secretos reales para que otra persona sepa que variables debe
  crear.

- flutter_native_splash.yaml
  Configuracion del splash nativo.

- android/
  Configuracion Android, launcher icon, splash y AndroidManifest.

- assets/
  Imagenes locales de la app, logo, splash y medios de pago.

- lib/
  Codigo principal de la aplicacion movil.

- test/ e integration_test/
  Pruebas unitarias, widgets e integracion.


Dentro de lib/:

- lib/main.dart
  Entrada principal de la app. Inicializa constantes, Supabase, notificaciones,
  deep links de pago y decide si mostrar login, home o pantalla de configuracion
  pendiente.

- lib/utils/
  Constantes y helpers generales.

- lib/models/
  Modelos de datos usados por pantallas y servicios.

- lib/services/
  Capa de comunicacion con Supabase, storage, funciones, carrito, pagos,
  ubicacion, tickets, preguntas, opiniones, favoritos, etc.

- lib/screens/
  Pantallas de la aplicacion separadas por modulo: auth, home, product,
  profile, tickets, quotes y payment.

- lib/widgets/
  Widgets reutilizables globales.


3. ARRANQUE DE LA APP

Archivo principal:

- lib/main.dart

Flujo:

1. Flutter inicia con main().
2. Se conserva el splash nativo mientras se preparan servicios.
3. Constants.init() lee valores inyectados por dart-define.
4. QuoteService.init() prepara cotizaciones locales.
5. Si existen SUPABASE_URL y SUPABASE_ANON_KEY, se inicializa Supabase.
6. NotificationService inicia notificaciones locales.
7. GoMedicalApp carga MaterialApp, tema visual y AuthGate.

Pantallas iniciales:

- MissingConfigScreen
  Sale cuando faltan credenciales de Supabase.

- AuthGate
  Revisa la sesion actual de Supabase.
  Si hay usuario y registro completo, abre HomeScreen.
  Si falta completar datos, abre RegistrationChecklistScreen.
  Si no hay sesion, abre LoginScreen.

  Gestiona solicitudes de cotizacion y contador local de cotizaciones.

- FavoriteService
  Alta, baja y consulta de favoritos.

- SearchService
  Maneja busquedas recientes y apoyo al buscador.

- QuestionService
  Gestiona preguntas de productos.

- ReviewService
  Gestiona opiniones, fotos, videos y permisos de opinion segun compras.

- AddressService
  Gestiona direcciones guardadas y direccion principal.

- LocationService
  Apoya en ubicacion/geolocalizacion y datos del cliente.

- TicketService
  Gestiona tickets y mensajes de soporte.

- NotificationService
  Gestiona notificaciones locales y realtime.

- MercadoPagoTestService

11. SEGURIDAD ACTUAL DE LA APP MOVIL

- Las credenciales no estan escritas directamente en lib/.
- Supabase se inicializa con variables de entorno de compilacion:
  SUPABASE_URL y SUPABASE_ANON_KEY.
- Google Sign-In usa client IDs por dart-define.
- ProductService pide columnas publicas explicitas para productos.
- MercadoPagoTestService no manda totales ni productos desde Flutter para crear
  la preferencia.
- La URL de Mercado Pago se valida antes de abrirse.
- Las operaciones sensibles deben quedar protegidas por RLS, RPC o Edge
  Functions en Supabase.

Puntos que deben revisarse en Supabase:

- Politicas RLS reales de cada tabla.
- Permisos de RPC y Edge Functions.
- Buckets privados para adjuntos sensibles.
- Que promociones y fechas se calculen en base de datos/backend, no con el reloj
  del telefono.


12. COMO MOSTRAR EL PROYECTO EN UNA REVISION

Orden recomendado para presentar la app:

1. Arranque y login.
   Mostrar login, registro y checklist.

2. Inicio.
   Mostrar busqueda, ubicacion, banners, categorias y productos.

3. Catalogo.
   Abrir categorias y subcategorias.

4. Producto.
   Mostrar ficha de producto, metodo de pago, opiniones, preguntas y productos
   relacionados.

5. Carrito.
   Agregar producto, cambiar cantidad, eliminar con icono, cupon y compra.

6. Direcciones.
   Mostrar seleccion, edicion y direccion principal.

7. Cotizaciones.
   Mostrar solicitud y listado desde perfil.

8. Opiniones y preguntas.
   Mostrar pantallas de perfil y detalle del producto.

9. Mantenimiento y soporte.
   Mostrar formulario de mantenimiento, tickets y chat de ticket.

10. Seguridad.
    Explicar que las credenciales estan fuera del codigo, que Mercado Pago se
    prepara desde backend y que Supabase debe tener RLS.

16. NOTAS PARA EL EQUIPO WEB / ADMINISTRATIVO

La app movil consume datos que deben estar correctamente creados en la parte web
administrativa o en Supabase:

- Categorias y subcategorias activas con sort_order.
- Banners y cards promocionales activos.
- Productos activos con imagenes publicas.
- Promociones calculadas por backend/base de datos.
- Cupones, si se habilita el flujo completo.
- Tickets de servicio y mensajes.
- Solicitudes de mantenimiento con todos los campos necesarios para seguimiento.
- Direcciones de clientes para envios.

Para evitar diferencias entre web y app, la base de datos debe ser la fuente de
verdad y la app solo debe leer los contratos publicos necesarios.

18. RESUMEN PARA PRESENTACION CORTA

"Go Medical es una app Flutter conectada a Supabase. La aplicacion separa las
pantallas en screens, la comunicacion con la base en services y los datos en
models. El home consume categorias, banners y productos desde Supabase. El
carrito y las direcciones tambien se guardan en base de datos. El pago con
Mercado Pago esta preparado para que el backend cree la preferencia, sin enviar
montos desde Flutter. La app incluye soporte, tickets, cotizaciones, opiniones,
preguntas y solicitudes de mantenimiento biomedico. Las credenciales se cargan
por dart-define y no deben subirse al repositorio."
